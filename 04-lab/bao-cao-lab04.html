MCP Server — ba tool đúng như tài liệu

Kết nối vào localhost:8085/mcp và hỏi list_tools(), server công bố đúng ba tool mà bảng trong README liệt kê:

list_tools() qua Streamable HTTP
Server: 'weather'  protocol=2025-11-25
So tool cong bo: 3
  - get_current_weather   params=['city']          required=['city']
  - get_forecast          params=['city','days']   required=['city']
  - health_check          params=[]                required=[]

Schema vẫn tự sinh từ type hints như bài 02 — get_forecast có days mang "default": 3 nên không nằm trong required, đúng với chữ ký get_forecast(city: str, days: int = 3).

gọi tool khi chưa có WEATHERAPI_KEY
health_check()
  ✅ Weather MCP Server is running!

get_current_weather('Hanoi')
  ❌ WeatherAPI key not configured. Please set WEATHERAPI_KEY…

health_check chạy trọn vẹn vì không cần khoá ngoài. Hai tool còn lại trả thông báo lỗi có kiểm soát thay vì ném exception — thiết kế tốt: agent nhận được câu giải thích đọc được thay vì lỗi kỹ thuật.

ADK làm đúng năm việc README mô tả

Thay vì chỉ mở giao diện web, agent được chạy trực tiếp qua Runner để in ra từng bước. Một lượt hoàn chỉnh bắt được như sau:

ADK Runner — vòng lặp function calling
USER: Kiem tra xem server thoi tiet co dang hoat dong khong?

  [Gemini yêu cầu] health_check({})
  [MCP server trả] {'content': [{'type': 'text',
     'text': '✅ Weather MCP Server is running! …'}]}
  [Gemini trả lời] Hệ thống thời tiết đang hoạt động.

Ba dòng này chứng minh trọn vẹn chuỗi trách nhiệm mà README vẽ:

  1. ADK kết nối MCP server qua StreamableHTTPConnectionParams
  2. McpToolset tự khám phá tool — agent không hard-code tên tool nào
  3. Ba tool được truyền cho Gemini dưới dạng function declarations
  4. ADK điều phối: Gemini chọn health_check, ADK gọi server, đưa kết quả về cho Gemini
  5. adk web phục vụ giao diện chat tại 127.0.0.1:8000

So với bài 01, khác biệt nằm ở chỗ không dòng code nào trong repo viết vòng lặp này. Bài 01 phải tự viết while resp.function_calls; ở đây ADK lo toàn bộ, lập trình viên chỉ khai báo Agent(model=…, tools=[weather_tools]).

Vấn đề phát hiện — đã sửa

Hai lỗi đầu đã được vá và chạy lại xác nhận. Việc sửa lỗi 1 còn làm lộ thêm hai lỗi nữa vốn bị nó che khuất: hai print() ghi ra stdout làm hỏng kênh JSON-RPC ở chế độ stdio, và EXPOSE 8080 trong Dockerfile trong khi app mặc định cổng 8085. Cả bốn nay đều đã sửa.

Lỗi 1 · chọn transport bằng isatty · weather.py:145

is_standalone = len(sys.argv) == 1 and sys.stdin.isatty() — server quyết định chạy HTTP hay stdio dựa vào việc stdin có phải terminal không. Chạy nền, chạy qua script, chạy trong CI đều không có TTY, nên server âm thầm rơi vào chế độ stdio và cổng 8085 không bao giờ mở, trong khi agent vẫn chờ ở localhost:8085.

Cách đi vòng không sửa code: đặt PORT=8085 để nhánh is_cloud_run nhận giá trị đúng.

Lỗi 2 · check sai đích · verify_setup.py:85

Hàm check_mcp_server() kiểm tra một URL Cloud Run hard-code từ lần triển khai của tác giả gốc, không phải localhost:8085 mà agent thực sự dùng. Script báo “✅ MCP server reachable” kể cả khi server nội bộ đang tắt — và sẽ báo đỏ nếu instance Cloud Run kia bị xoá, dù bài lab hoàn toàn bình thường.

Quan sát · mô tả tool làm nhiễu model

Chuỗi trả về của health_check có câu “Ready to provide weather data for Australian cities and worldwide”. Khi hỏi tiếp về Hà Nội trong cùng phiên, Gemini từ chối gọi get_current_weather và trả lời rằng nó chỉ hỗ trợ các thành phố Úc. Nội dung tool trả về đã trở thành ràng buộc ngoài ý muốn lên hành vi model.

Bảo trì · phụ thuộc đã ngừng hỗ trợ

mcp-client/pyproject.toml khai báo google-generativeai. Gói này đã ngừng phát triển; import nó sinh FutureWarning yêu cầu chuyển sang google-genai. Agent không thực sự dùng gói này — có thể gỡ khỏi dependencies.

Dockerfile — build và chạy thật

Thư mục mcp-server có sẵn Dockerfile nhắm tới Cloud Run. README không nhắc tới nó, nên nó chưa từng được kiểm chứng. Build thành công, image 326 MB:

docker build -t weather-mcp:lab04 .
#11 naming to docker.io/library/weather-mcp:lab04  done
#11 DONE 7.1s

Chạy container đúng như CMD định nghĩa lộ ra chính lỗi isatty ở trên, lần này ở dạng nguy hiểm hơn:

docker run --rm -p 8086:8080 weather-mcp:lab04
✅ MCP server initialized with Streamable HTTP transport
🔧 Available tools: get_current_weather, get_forecast, health_check
Starting FastMCP server in stdio mode for local client

Hai dòng này mâu thuẫn nhau. Dòng đầu là print() vô điều kiện ở weather.py:138, luôn khẳng định đang dùng HTTP. Dòng cuối mới là sự thật: container không có TTY nên rơi vào stdio, và cổng 8080 không bao giờ mở dù EXPOSE 8080 và -p đã khai báo.

Thêm -e PORT=8080 thì chạy đúng, và MCP hoạt động xuyên qua container — đủ 3 tool, health_check trả kết quả bình thường:

docker run -e PORT=8080 -p 8086:8080 · rồi list_tools qua :8086
Uvicorn running on http://0.0.0.0:8080
lab04-test-b  Up 6 seconds  0.0.0.0:8086->8080/tcp

Server: 'weather'  protocol=2025-11-25
So tool cong bo: 3
health_check() -> ✅ Weather MCP Server is running!

Trên Cloud Run thì Dockerfile này vẫn chạy đúng, vì nền tảng tự đặt biến PORT. Nhưng chạy docker run ở máy — cách kiểm thử image trước khi deploy — thì im lặng hỏng. Đây là kiểu lỗi chỉ lộ ra đúng lúc người ta cần nó nhất.

Dữ liệu thời tiết thật

Sau khi có WEATHERAPI_KEY, cả ba tool trả dữ liệu thật từ WeatherAPI.com. Lưu ý API_KEY được đọc một lần lúc import (weather.py:16) nên phải khởi động lại server sau khi đặt biến — và weather.py không nạp dotenv, nên file .env ở thư mục server sẽ không có tác dụng.

get_current_weather('Hanoi')

Toàn bộ ngăn xếp — chạy thật từ đầu đến cuối

Với dữ liệu thật đã thông, agent được chạy lại để kiểm chứng chuỗi đầy đủ: ADK → Gemini chọn tool → MCP server → WeatherAPI → Gemini tổng hợp.

ADK Runner · dữ liệu thật
USER: Du bao Da Nang 3 ngay toi co mua khong?

  [Gemini yêu cầu] get_forecast({'city': 'Danang', 'days': 3})
  [MCP trả] 'Weather Forecast for Danang… 2026-08-28: High 29.8°C…'
  [Gemini trả lời]
   • 28/08: nhiều mây, khả năng mưa thấp (28%)
   • 29/08: nhiều mây, mưa tăng nhẹ (36%)
   • 30/08: khả năng cao có mưa (90%)
   Tóm lại… ngày thứ ba khả năng mưa rất lớn, nên chuẩn bị áo mưa hoặc ô.

Đây là điểm khác biệt lớn nhất so với bài 01. Gemini không chỉ đọc lại số liệu — nó tổng hợp qua ba ngày và rút ra kết luận hành động (“ngày thứ ba khả năng mưa rất lớn”). Toàn bộ vòng lặp do ADK điều phối; không dòng code nào trong repo viết nó.

Còn lại: khoá Gemini bị giới hạn IP

Khoá ghi trong mcp-client/.env bị chặn IP 14.238.145.226 với 403 API_KEY_IP_ADDRESS_BLOCKED. Một khoá khác trên máy không bị giới hạn và chạy tốt, nhưng ở tier khác nên gemini-2.5-flash trả 404; hai model dùng được là gemini-3-flash-preview và gemini-3.1-flash-lite. Mọi kết quả ở trên chạy bằng cấu hình thay thế này.
